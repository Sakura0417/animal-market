## 0. 结论速览（先说重点）

| 议题 | 结论 |
|---|---|
| 农场动物布局 | **建议网格化**：牧场划分为等尺寸 n 格，动物占据整格、仅上下左右 4 朝向、紧密排列。这是对现有"散点 + 走廊遮挡"的**升级重构**，语义更清晰、性能更好、且为后续关卡编辑器铺路 |
| 碰撞引擎迁移 | **明确不建议迁移到 Cocos 自带物理引擎**（Box2D / builtin 2D 均否）。现有"解析式规则查询"正是这类玩法（猪了个猪 / 挪车）的正确解法，网格化后它会更简单而不是更复杂 |
| 碰撞语义变化 | 走廊遮挡（同列/同行任意距离内有动物即被挡）→ **相邻格遮挡**（朝向的下一格被占即被挡），与参考图玩法语义一致 |
| 附带收益 | 修复一个现存隐患：`blockerOf()` 返回"数组序首个"而非"最近的"遮挡者，碰撞动画可能穿越近处动物冲向远处动物（详见 §2.4） |
| 实施时机 | 建议放在 **Game.scene 创建与运行时冒烟之前**——网格化会大改 core 布局与 PenView 渲染，先冒烟再改等于返工两轮 |
| 最大代价 | 难度曲线全部重标定：网格是新机制，现有 4,800 局曲线与原型种子对拍基线作废，需用 BalanceSim 重建（工程已有此能力，成本低） |

- **编辑器连接**：正常（响应 5ms），工程于分析当日处于打开状态。
- **脚本资产**：`db://assets` 下共 **19 个 TS 脚本**已注册（core 5 / view 9 / services 2 / platform 1 / GameView 1）。
  - 值得注意：**GameView.ts 已存在**（交接文档 2026-09-05 时标记为"缺失"）——项目在交接后已有推进，A1 行动项实质完成。
- **场景层级**：当前场景仅有 `Main Light` + `Main Camera`，**Game.scene 仍未创建**，GameView 未挂载——运行时冒烟（A3）尚未发生。
- **布局事实**（GameView.buildLayout 实测常量）：牧场区 `penW = 286`、`penH ≈ 478` 设计像素（375 设计宽，两侧留白 12 + 土路带 32.5）；动物显示尺寸 `sz = penW × 0.152 ≈ 43.5`。

### 2.2 现有"碰撞引擎"的真实实现方式

本项目**根本没有物理意义上的碰撞引擎**，而是一套**纯解析式（analytic）规则查询**，分布在三层：

**① core 层判定（数值唯一来源，零 cc 依赖）** —— `Board.ts` / `GameSession.ts`

```
走廊遮挡算法 blockerOf(herd, b)：
  对 herd 中每只动物 a（a ≠ b）：
    若 b 朝上 且 a.yu < b.yu − AHEAD 且 |a.x − b.x| < TOL → a 是遮挡者
    （下/左/右对称）
  即：b 的朝向射线上、横向容差 TOL 内，存在任何动物 → b 被挡
```

- 常量（`Constants.ts`）：`R = 7.6`（动物半径，核心坐标单位）、`TOL = R×1.22 ≈ 9.3`（横向容差）、`AHEAD = R×0.55 ≈ 4.2`（前瞻距离）、`MIN_D = R×1.58 ≈ 12`（散点最小间距）。
- **关键语义**：这是**无限远走廊**——同一列上方任意距离只要有动物就算被挡，不是"相邻才挡"。
- 位置来源：`scatter(n, minD)` 在 100×125 归一化空间内做"最优努力"泊松式采样（每点最多 220 次尝试）；朝向由 `smartDir()` 以 50% 概率偏向最近边界。
- 玩法裁决：`takeAnimal(uid)` —— 未被挡 → 飞入围栏；被挡 → 扣 1 生命（碰撞）或吊车免罚吊走。

**② view 层命中（PenView.onTap）**

点击时把触点换算为 pen 本地坐标，在节点池中找**距离最近**的动物，半径阈值 `sz × 0.62` 内才生效——圆形最近邻匹配，非精确命中。

**③ view 层碰撞动画（AnimalNodeC.bonk + GameView.takeAnimal）**

被挡动物点击后：GameView 调 `blockerOf()` 取遮挡者 → 按朝向投影算出接触距离 `hitDist` → bonk 沿朝向**真实走到接触点**（≈380px/s）→ 接触瞬间红闪 + 粒子 + "-1 生命"飘字 + 震屏 + 心碎 → 过冲弹回原位。

**④ 验证体系**：`tools/sim/BalanceSim.ts` 在 Node 22 下直跑 core（无引擎依赖），mulberry32 种子对拍 12/12 通过，4,800 局难度曲线已归档。

### 2.3 现有实现的优点（迁移评估的前提，必须承认）

1. **确定性与可复现**：纯函数 + 种子随机流，Node 可直跑、跨平台结果一致——这是本项目难度资产（验证过的曲线）的根基。
2. **性能**：点击时一次 O(n) 线性扫描（n≤34），无每帧成本。
3. **零包体**：不引入任何物理运行时（微信首包 4MB 红线下很关键）。
4. **语义与玩法同构**："被挡"是**规则问题**而非**物理问题**，解析查询给出的是精确、可断言的答案。

### 2.4 现有实现的问题清单（网格化要解决的正是这些）

| # | 问题 | 现状出处 | 网格化后 |
|---|---|---|---|
| P1 | **走廊语义反直觉**：前方隔了 3 个空格、再前面有动物也算被挡。玩家"眼前明明是空的却撞了"，与猪了个猪/挪车的直觉相悖 | `blockerOf` 无距离上限 | 相邻格判定，直觉即规则 |
| P2 | **`blockerOf` 返回数组序首个而非最近遮挡者**：碰撞动画可能穿过近处动物冲向远处动物（hitDist 按错误目标计算）。散点 + TOL 容差下，L10+（30 动物 + 4 岩石挤在 100×125）同一走廊 Multiple 动物的概率不低 | `Board.ts` L36-46 按数组序返回 | 相邻格唯一确定，隐患自然消失 |
| P3 | **散点生成不可控**：`scatter()` 是重试式采样（220 次/点仍可能不满足 MIN_D）；`generate()` 外层再套 40 次重试保解锁数 ≥6。布局质量靠运气，密度高时挤成一团 | `Board.ts scatter` / `GameSession.generate` | 约束式填充，密度、连通性皆可控 |
| P4 | **命中判定是"最近圆匹配"**：两只动物贴近时可能点 A 判成 B（0.62×sz 阈值内的最近者胜出） | `PenView.onTap` | 点格即命中，零歧义、O(1) |
| P5 | **紧密排列与视觉随机量冲突**：动物节点有 ±26° 随机倾斜（view 层装饰），散点下是"自然感"，紧密排列下就是"没对齐" | `AnimalNodeC` 构造 `node.angle` | 去掉或降至 ±3° |
| P6 | **数值与视觉耦合出 bug 的温床**：TOL/AHEAD/MIN_D/R 四个常量与精灵尺寸 `sz = penW×0.152` 分居两层，改任何一个都要脑内联立方程（GameView 碰撞分支里 `2 × coreRadiusPx() × 0.95` 这类换算就是证据） | GameView L348 | 格距 = 唯一空间常量，接触距离变成确定性公式 |
| P7 | **无法手工设计关卡**：散点 + 随机数生成，布局不可编辑、不可复现给他人 | — | 格子即数据，编辑器成为可能（§3.6） |

## 3. 农场网格化布局设计方案

### 3.1 设计原则

1. **格子是唯一空间语言**：core 只认 `col/row` 整数坐标；像素换算只发生在 PenView 一处。
2. **朝向保持 4 向**：现有 `Dir = 'up'|'down'|'left'|'right'` 类型原样沿用（本项目已是 4 朝向，此条零成本满足）。
3. **紧密排列**：动物占满整格、相邻贴合，格距即动物间距——"挪车场"的视觉观感。
4. **core 纪律不变**：网格判定仍是纯函数、零 cc 依赖、Node 可直跑、种子可复现——验证体系原样保留。

### 3.2 数据模型变更（示意，非代码）

```
Animal:  { uid, type, dir, col, row, rare, obstacle }     // x/yu 浮点 → col/row 整数
新增:    Grid = { cols, rows, occ(col,row) → Animal|null }  // 占用图（O(1) 查询）
退役:    R / TOL / AHEAD / MIN_D / PAD / ASPECT            // 由 GRID_COLS / GRID_ROWS / CELL_PITCH 取代
```

### 3.3 遮挡判定新语义（核心规则变更）

> **被挡 ⟺ 朝向的相邻格被占用（动物或岩石）。** 边界格朝外视为空（可以走出，衔接现有土路行走动画）。

| 对比项 | 现状（走廊遮挡） | 网格化（相邻遮挡） |
|---|---|---|
| 被挡条件 | 同列/同行任意距离内有动物（横向容差 TOL） | 朝向下一格被占 |
| 查询成本 | O(n) 遍历 | **O(1)** 占用图查表 |
| 边界情况 | TOL 容差导致的"半挡不算挡"灰色地带 | 不存在 |
| 修复中的连锁解锁 | 有（移走走廊动物解锁一串） | 有且更强（移走相邻动物即解锁，类似挪车"腾车位"的爽感） |
| 初始可动数量 | 偏少（整列整行被锁） | 偏多（只有被贴脸的才锁）→ 用密度补偿难度（§3.5） |

### 3.4 网格规格建议（按现有版面换算）

牧场实际区域 286 × 478 设计像素，动物显示尺寸 ≈ 43.5：

| 方案 | 格子 | 容量 | L12 现密度(34 只)填充率 | 定位 |
|---|---|---|---|---|
| **A（推荐起步）** | 6 列 × 10 行 | 60 格 | ≈ 57% | 视觉最接近现有尺寸，教学期宽松 |
| B | 5 列 × 8 行 | 40 格 | 85% | 挪车式高压，适合高关卡 |
| C（关卡参数化） | 由 LevelCfg 逐级给 cols/rows | — | — | 最终形态：密度成为难度旋钮 |

**建议**：物理网格固定 6×10（格距 ≈ 47.7，取 `sz = 格距 × 0.92 ≈ 43.8`，与现有精灵尺寸几乎一致——**视觉零回归**），密度通过 `LevelCfg` 控制动物/岩石数量实现难度梯度；后期再开放行列数参数化。

### 3.5 生成算法建议（约束式，替代散点重试）

```
1. 空网格 → 随机放岩石（obstacle 格）
2. 随机放动物（类型轮转 + 稀有掷点，随机流结构与现版一致以保留种子纪律）
3. 朝向分配：smartDir 的网格版——优先朝"空格/边界外"，高关卡反向偏置（朝向被占格制造链条）
4. 保底修复：解锁数 < 6 时，翻转若干被挡动物朝向指向空格（确定性修复，替代现 40 次整体重试）
5. 产出可直接序列化为关卡 JSON（§3.6 的数据源）
```

难度补偿预判（**需重跑模拟器确认**，此处仅定性）：相邻遮挡比走廊遮挡"松"，早期关卡会更简单、中后期因贴身链条产生连消爽感与扣心压力的节奏变化。建议同步调高 L6+ 密度（岩石数量 + 动物数）与订单复杂度，由 BalanceSim 找新平衡点。

### 3.6 关卡编辑器路线图（对标图 1，三阶段渐进）

**Phase A —— 数据 schema 先行（随网格化一并落地，成本≈0）**

定义关卡 JSON（仅 schema，生成器输出即此格式）：

```
{ cols, rows, rocks: [[c,r],...], animals: [{ col, row, dir, type, rare }] }
```

**Phase B —— 编辑器本体（P6 期，二选一）**

## 4. 碰撞引擎评估：是否迁移到 Cocos 自带物理引擎

### 4.1 结论：**不迁移。** 现有解析式 + 网格化升级，是这类玩法的终态正解

Cocos Creator 3.8 提供 2D 物理两档：`builtin`（轻量，仅 AABB/圆重叠事件）与 `Box2D`（完整刚体动力学）。逐维度对比：

| 评估维度 | 解析式（现状 → 网格化） | Cocos 物理（Box2D） | Cocos 物理（builtin） |
|---|---|---|---|
| **判定语义** | 规则查询：点击时刻"这只动物被挡吗"——**精确、瞬时、可断言** | 连续碰撞：求解器迭代近似、依赖帧率与步长 | 仅运动体重叠事件，仍需自建规则层 |
| **确定性 / 种子对拍** | ✓ 已验证 12/12；网格化后更强（O(1) 查表） | ✗ 浮点跨平台差异 + 迭代顺序敏感，**种子对拍体系直接报废** | ✗ 事件时序依赖帧循环 |
| **Node 无头模拟** | ✓ core 零 cc，BalanceSim 直跑（4,800 局曲线的来源） | ✗ 物理只在 cc 运行时内存在 | ✗ 同左 |
| **包体（微信 4MB 首包红线）** | 0 KB | Box2D WASM 数百 KB 级 | 较小但非零 |
| **每帧成本** | 0（点击时才查询） | world.step() 常驻 | 广播常驻 |
| **与玩法匹配度** | 本玩法是**回合制规则判定**，动物静止待命、运动全是编排好的 Tween（飞行/走路/弹回） | 为"连续动力学"（重力/速度/恢复系数）设计，本项目一样用不上 | 同左 |
| **脚本动画的假碰撞** | 无此问题 | ✗ flyAnimal/walkPath 的**路过**会触发真实接触事件，需再用碰撞分组屏蔽，负收益 | 同左 |
| **调试与回归** | 纯函数，单测/断言直接写 | 断点难、复现难 | 中 |

### 4.2 一句话论证

> 这款游戏的"碰撞"是**玩法规则的裁决**（被挡 → 扣血/弹回），不是**物理世界的仿真**。规则需要精确和可复现，物理引擎提供的是近似和不可复现——**用它等于花包体和确定性，买一个我们不需要的答案**。而碰撞的"打击感"（冲撞、红闪、过冲弹回、震屏）本质是编排动画，现有 Tween 链（bonk）做得比物理恢复系数更可控、更好调。

### 4.3 什么情况下才值得重新考虑物理

- 玩法转向**实时动力学**（动物有质量/惯性/推挤，如"彗星撞动物"类）；
- 需要大规模**连续物理特效**（金币堆坍塌等）且 Tween 无法胜任。
两者均与当前 PRD 无关；若未来真有此需求，也应作为**独立的特效子系统**局部引入，而非替换 core 判定。

### 4.4 网格化后碰撞查询的最终形态

```
被挡查询 = occ(col + dCol, row + dRow) ≠ 空        // O(1)
碰撞接触距离 = CELL_PITCH − SPRITE_SIZE            // 常量，无需逐次计算
解锁集 = 遍历格子查 4 邻域                          // O(n)，n≤34
```

整个"碰撞引擎"收敛为**一张占用哈希表 + 一个方向向量**——这是最小完备实现，没有留给物理引擎的改进空间。
