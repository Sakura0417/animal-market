## 20:35 刘海安全区量纲错误 + 草地渐变 6→96 段

用户反馈「顶部被刘海遮挡、底部被 Home 条遮挡」+「隐藏农场划分格子的横/纵辅助线」。逐项查证后：**两项都不是"没做"，而是"做错/做偏"**。

**① 安全区：根因是量纲错误。**
旧写法 `topIn = wx.safeArea.top / s`。`wx.safeArea.top` 单位是**逻辑 px**（刘海机型 = 44），而 `view.getVisibleSize()` 返回**物理像素**（375pt @2x ⇒ vis = 750×1624）⇒ `s = 2` 的含义是「物理 px / 设计单位」。于是 `44 / 2 = 22`，**只有正确值的一半**；底部同理 `34 / 2 = 17`。与截图完全吻合：HUD 只下移 22pt 仍被刘海压住、道具栏只抬 17pt 仍压在 Home 条上。
修：改用 `sys.getSafeAreaRect()`（引擎内部已 `_convertToUISpace`，与 vis 同坐标系），`top = (vis.h − sa.y − sa.height)/s`、`bottom = sa.y/s`。非异形屏返回等大 Rect ⇒ inset 恒 0，普通屏逐像素不变；预览/浏览器同 API ⇒ 预览即真机。同时**删除** `PlatformAdapter.getSafeInsets()`（量纲错误的旧源 + 零调用点，留着必被误用）。加启动日志便于真机一眼验证。
**引擎依据**（以后直接读源码定案，别猜）：`E:\ProgramData\cocos\editors\Creator\3.8.8\resources\resources\3d\engine\cocos\ui\safe-area.ts` 第 117–124 行（`widget.bottom = sa.y`）。

**② 格线：其实早已移除，"横向分界"的真身是草地渐变色带。**
三层证据：a) 源码自 17:58 起不画格线（`onTap` 的 `GRID_COLS×GRID_ROWS` 点格命中逻辑完好）；b) 构建产物（19:55）里的 `PenView` 只有「6 段渐变色带 + 虚线边框」，**无任何网格 line/stroke**；c) 对截图做逐行/逐列亮度剖面：横向分界间距 ≈ **牧场高/6**（≈91 image px），而格线应为 **高/10**（≈56px）；逐列最大偏差仅 **1.3** ⇒ **无纵向线**。
⇒ 6 段色带单步色差 = 总色差 1/5、R 通道跨 38 级 ⇒ **单步 7.6 级**，远超平滑渐变 2–3 级的可辨阈值。
修：色带 **6 → 96 段**，单步 ≈0.6 级（低于 1 级量化精度）⇒ 不可能看见；圆角帽各占 2 段取中值色 ⇒ 无接缝。这也把「6 段近似 linear-gradient」的**原始意图真正落实**——段边界本就是近似误差。

**③ 工具**：`tools/contact-sheet.py` 解码器原先只支持 8bit RGBA，读不了微信截图（ctype=2 RGB）→ 扩展为 RGB/RGBA 通吃、统一输出 RGBA。新增 `tools/crop-boost.py`（裁剪 + 对比度增益）、`tools/row-profile.py`（逐行/逐列亮度剖面，用数值判定"有没有线"）。

**验证**：tsc **存量 11 条、零新增**；活跃 chunk `f10a9f09`（import-map 已引用，20:33）含 `getSafeAreaRect` / `safeInsetsInDesignUnits`，且 `getSafeInsets` 已从产物消失；PenView 产物含 `shade` / `/96`；安全区数值手工复核 → top=44 / bottom=34（旧 22 / 17）。

⚠️ **必须重新构建微信包才能验证**：devtools 读的是**构建产物**而非源码；MCP 的 build 只支持 web-mobile/web-desktop/ios/android/windows/mac，**没有 wechatgame**，无法代劳。
